Pusula integriert drei Kategorien von CLI-Tools, die auf drei separate Dashboard-Seiten verteilt sind:

| Seite          | Route                   | Konzept                                                                           | Anzahl              |
| -------------- | ----------------------- | --------------------------------------------------------------------------------- | ------------------- |
| **CLI Code's** | `/dashboard/cli-code`   | Coding-Tools, die auf Pusula verweisen (Client → CLI → Pusula → Anbieter)   | 26                  |
| **CLI Agents** | `/dashboard/cli-agents` | Autonome Agenten, die auf Pusula verweisen (gleicher Ablauf, breiterer Umfang) | 10                  |
| **ACP Agents** | `/dashboard/acp-agents` | CLIs, die Pusula über stdio/ACP als Backend startet (umgekehrter Ablauf)       | siehe Registrierung |

Alte Routen werden per 308 weitergeleitet: `/dashboard/cli-tools` → `/dashboard/cli-code`, `/dashboard/agents` → `/dashboard/acp-agents`.

## So funktioniert es

```
CLI Code's / CLI Agents (Konsumfluss):
Claude / Codex / OpenCode / Cline / KiloCode / Continue / Hermes Agent / Goose / ...
           │
           ▼  (alle verweisen auf Pusula)
    http://YOUR_SERVER:20128/v1
           │
           ▼  (Pusula leitet an den richtigen Anbieter weiter)
    Anthropic / OpenAI / Gemini / DeepSeek / Groq / Mistral / ...

ACP Agents (umgekehrter Erzeugungsfluss):
    Client-Anfrage → Pusula → erzeugt CLI über stdio/ACP → Antwort
```

**Vorteile:**

- Ein API-Schlüssel zur Verwaltung aller Werkzeuge
- Kostenverfolgung über alle CLIs im Dashboard
- Modellwechsel ohne Neukonfiguration jedes Werkzeugs
- Funktioniert lokal und auf Remote-Servern (VPS, Docker, Akamai, Cloudflare Tunnel)

## Automatische Konfiguration mit `setup-*`

Sie müssen die Konfiguration jedes Tools nicht manuell schreiben. Pusula liefert einen `setup-*`-Befehl pro unterstütztem CLI, der den **aktuellen** Modellkatalog von einem laufenden Pusula (lokal oder remote) liest und die eigene Konfiguration des Tools auf Ihrer Maschine schreibt:

```bash
pusula setup-codex        pusula setup-claude       pusula setup-opencode
pusula setup-cline        pusula setup-kilo         pusula setup-continue
pusula setup-cursor       pusula setup-roo          pusula setup-crush
pusula setup-goose        pusula setup-qwen         pusula setup-aider
pusula setup-5dive
```

Jeder akzeptiert `--remote <url> --api-key <key>` (konfiguriert ein lokales Tool gegen ein entferntes Pusula), `--dry-run` (Vorschau ohne Schreiben) und `--port`. Tools ohne Modell-Auto-Erkennung (Cline, Kilo, Roo, Goose, Aider, Qwen, 5dive) verwenden `--model <id>` (und `--yes` für nicht-interaktive Ausführungen). `setup-5dive` ist die einzige Methode, die nicht unter `$HOME` schreibt: Sie konfiguriert eine 5dive-Agentenflotte, indem sie ein Root-eigenes Authentifizierungsprofil auf dem Flotten-Host schreibt, sodass es über `sudo` neu ausgeführt wird und keinen eigenen Remote-Modus hat. Um ein CLI mit der richtigen Umgebung und ohne geschriebene Konfiguration zu starten, verwenden Sie den generischen `pusula run <target>` Launcher (claude, codex, aider, goose, opencode, qwen, gemini – Targets und Aliase stammen aus `bin/cli/cli-manifest.mjs`); die älteren Launcher pro Tool `pusula launch` (Claude Code) und `pusula launch-codex` (Codex) bleiben verfügbar. Gemini CLI ist nur zum Starten gedacht: Es ist ein `pusula run`-Target, hat aber keine `setup-*`/`configure`-Methode.

> **Vollständige Referenz:** Die Master-Tabelle – was jeder Befehl schreibt, jedes Flag, lokal vs. remote und welche Tools ein `/v1`-Suffix benötigen – befindet sich in **[CLI-Integrationen](../guides/CLI-INTEGRATIONS.md)**.

### Ausführung in einem Container

Ein `setup-*`-Befehl, der innerhalb des Pusula-Containers ausgeführt wird, schreibt in das eigene Home-Verzeichnis des Containers, das kein Host-CLI liest und das mit dem Container verschwindet. Pusula erkennt dies und beendet sich mit `2` und Anweisungen, anstatt zu schreiben. Zwei unterstützte Wege sind – installieren Sie das CLI auf dem Host und `pusula connect` zum Container, oder binden Sie die Konfigurationsverzeichnisse ein und setzen Sie `CLI_CONFIG_HOME` (das Compose `host`-Profil). Jeder `setup-*`-Befehl, plus `pusula configure` und `pusula config set`, akzeptiert `--allow-container-write`, wenn Sie tatsächlich die Konfiguration der eigenen CLIs des Containers beabsichtigt haben; `PUSULA_ALLOW_CONTAINER_CONFIG_WRITE=true` bewirkt dasselbe für den Server. Siehe [Docker-Handbuch → Konfigurieren von Host-CLI-Tools](../guides/DOCKER_GUIDE.md#configuring-host-cli-tools-when-pusula-runs-in-docker).

Der **Anwenden-Endpunkt** des Dashboards (`POST /api/cli-tools/apply`) erzwingt dieselbe Schutzmaßnahme: In einem Container antwortet ein Schreibvorgang, dessen Ziel nicht vom Host eingebunden ist, mit **`422`** und `containerEphemeralTarget: true`, dem sicheren Fehlertext und – für die Tools mit einer Host-Methode (claude, codex, opencode, cline, kilo, continue) – einem `hostSetupCommand` (z.B. `pusula setup-opencode`), das stattdessen auf dem Host ausgeführt werden soll; es wird nichts geschrieben. `dryRun: true` funktioniert weiterhin im Container-Modus und gibt eine redigierte Vorschau + Zielpfad zurück, ohne die Festplatte zu berühren. Der Vorschauinhalt ist keine Anmeldeinformationen enthaltende Konfiguration zum Kopieren oder Importieren. Wenden Sie die Konfiguration mit dem ursprünglichen Tool/der Basis-URL/dem API-Schlüssel/den Modelleingaben auf dem Host an oder verwenden Sie den angegebenen Host-seitigen Setup-Befehl. Siehe [CLI-Konfigurationssicherheit](../security/CLI-CONFIGURATION.md) für den Vorschau-Header und den Anforderungsvertrag. Dieses Verhalten ist beabsichtigt und durch `tests/unit/api/cli-tools/apply-container-guard.test.ts` regressionsgeschützt – beheben Sie niemals einen 422-Fehler, indem Sie die Schutzmaßnahme entfernen.

## Quelle der Wahrheit

Der einheitliche Katalog befindet sich in `src/shared/constants/cliTools.ts` als `CLI_TOOLS: Record<string, CliCatalogEntry>`.

Jeder Eintrag hat diese Felder (definiert in `src/shared/schemas/cliCatalog.ts`):

| Feld                                            | Typ                                                          | Beschreibung                                                                   |
| ----------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `category`                                      | `"code" \| "agent"`                                          | Auf welcher Seite das Tool erscheint                                           |
| `vendor`                                        | `string`                                                     | Herkunft des Tools ("Anthropic", "OSS (P. Gauthier)")                          |
| `acpSpawnable`                                  | `boolean`                                                    | Auch als ACP-Agent nutzbar (Abzeichen angezeigt)                               |
| `baseUrlSupport`                                | `"full" \| "partial" \| "none"`                              | Unterstützungsgrad für benutzerdefinierte Endpunkte. `"none"` = MITM-Rückstand |
| `configType`                                    | `"env" \| "custom" \| "guide" \| "custom-builder" \| "mitm"` | Konfigurationsmechanismus                                                      |
| `id`, `name`, `color`, `description`, `docsUrl` | standard                                                     | Kernanzeigefelder                                                              |

Einträge mit `baseUrlSupport: "none"` werden **nicht angezeigt** auf den Dashboard-Seiten — sie sind im MITM-Rückstand für Plan 11 registriert (siehe `_tasks/features-v3.8.6/refactorpages/_orchestration/_plan11-mitm-backlog.md`).

### Fähigkeitsstufen (katalogisiert × erkennbar × konfigurierbar × startbar)

Nicht jedes katalogisierte Tool ist erkennbar, konfigurierbar oder startbar. Jede Stufe hat eine deklarierende Quelle, und ein Drift-Test hält sie synchron:

| Stufe              | Bedeutung                                                                           | Deklariert in                                                     |
| ------------------ | ----------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| **Katalogisiert**  | Erscheint im Dashboard-Katalog (Name, Anbieter, Dokumentation, Konfigurationstyp)   | `src/shared/constants/cliTools.ts` (`CLI_TOOLS`)                  |
| **Erkennbar**      | Binär-/Konfigurationsdetektion, Gesundheitsprüfungen, Konfigurationspfade           | `src/shared/services/cliRuntime.ts` (`CLI_TOOLS` Laufzeitkatalog) |
| **Konfigurierbar** | Unterstützt durch `pusula configure <cli>` (Setup-Rezept vorhanden)              | `bin/cli/cli-manifest.mjs` (`configure: true`)                    |
| **Startbar**       | Unterstützt durch `pusula run <target>` (Umgebungs-/Argumenteinfügung definiert) | `bin/cli/cli-manifest.mjs` (`run: true`)                          |

`bin/cli/cli-manifest.mjs` ist das kanonische ausführbare Manifest für die CLI-Befehle: `run`, `configure` und die Shell-Vervollständigungs-Generatoren leiten ihre Ziel-Listen, Alias-Auflösung (zum Beispiel `kilocode`/`kilo-code`/`kilo_cli` → `kilo`) und die Verkabelung des `--model`-Flags davon ab. Der Drift-Wächter `tests/unit/cli/cli-manifest-drift.test.ts` stellt sicher, dass das Manifest, der Laufzeitkatalog, der UI-Katalog und jede Verbraucherschnittstelle synchron bleiben — ein Ziel, das einer Oberfläche hinzugefügt wird, ohne dass die anderen aktualisiert werden, führt zum Fehlschlagen der Suite, anstatt stillschweigend abzuweichen.

## 5. Batch Detection API

Alle Werkzeugerkennungen werden über einen einzigen Endpunkt aggregiert:

**`GET /api/cli-tools/all-statuses`**

- Auth: `requireCliToolsAuth(request)` (gleich wie bei anderen `/api/cli-tools/` Routen)
- Gibt zurück: `Record<toolId, ToolBatchStatus>` (Typ: `src/shared/types/cliBatchStatus.ts`)
- Strategie: `Promise.all` über alle Werkzeuge, 5s Timeout pro Werkzeug
- Cache: In-Memory LRU, indiziert nach Konfigurationsdatei `mtime`. Cache wird ungültig, wenn sich mtime ändert. Wird beim Neustart des Servers zurückgesetzt.

Antwortstruktur pro Werkzeug:

```ts
interface ToolBatchStatus {
  detection: {
    installed: boolean;
    runnable: boolean;
    version?: string;
    command?: string;
    commandPath?: string;
    reason?: string;
  };
  config: {
    status: "configured" | "not_configured" | "not_installed" | "unknown" | "other";
    endpoint?: string | null;
    lastConfiguredAt?: string | null;
  };
  error?: string; // bereinigt, keine Stack-Traces
}
```

## 9. Schnellstart

### Schritt 1 — Holen Sie sich einen Pusula API-Schlüssel

1. Öffnen Sie `/dashboard/api-manager` → **API-Schlüssel erstellen**
2. Geben Sie ihm einen Namen (z.B. `cli-tools`) und wählen Sie alle Berechtigungen aus
3. Kopieren Sie den Schlüssel — Sie benötigen ihn für jede CLI unten

> Ihr Schlüssel sieht so aus: `sk-xxxxxxxxxxxxxxxx-xxxxxxxxx`

---

### Schritt 2 — Installieren Sie die CLI-Tools

Alle npm-basierten Tools erfordern Node.js 22.22.2+ oder 24.x:

```bash
pip install aider-chat

# Pi-Coding-Agent
# siehe https://github.com/zechnerj/pi-coding-agent für die Installation

# jcode

```

### Schritt 3 — Konfigurieren Sie über das Dashboard

1. Gehen Sie zu `http://localhost:20128/dashboard/cli-code`
2. Finden Sie Ihr Tool im Raster
3. Klicken Sie auf die Karte, um die Detailseite des Tools zu öffnen
4. Wählen Sie Ihren API-Schlüssel und die Basis-URL aus
5. Klicken Sie auf **Konfiguration anwenden** oder kopieren Sie den manuellen Konfigurationsausschnitt

```bash
# Pusula Universeller Endpunkt
```

> z.B. `http://<your-server-ip>:20128`.

#### VS Code Insiders (`chatLanguageModels.json`)

Verwenden Sie dies, wenn VS Code Insiders für benutzerdefinierte Endpunktmodelle konfiguriert ist und Sie möchten, dass Pusula ohne ein benutzerdefiniertes Headerfeld funktioniert.

**Empfohlener Speicherort:**

- Linux: `~/.config/Code - Insiders/User/chatLanguageModels.json`
- Windows: `%APPDATA%/Code - Insiders/User/chatLanguageModels.json`

**Beispiel unter Verwendung des tokenisierten Pusula-Alias:**

```json
[
  {
    "vendor": "customendpoint",
    "id": "auto",
    "name": "Pusula Auto",
    "family": "gpt-4",
    "version": "1.0.0",
    "url": "http://localhost:20128/api/v1/vscode/sk-your-pusula-key/chat/completions",
    "modelsUrl": "http://localhost:20128/api/v1/vscode/sk-your-pusula-key/models",
    "requestFormat": "openai-chat-completions",
    "contextWindow": 256000,
    "maxOutputTokens": 32768,
    "auth": {
      "type": "none"
    }
  }
]
```

**Hinweise:**

- Ersetzen Sie `sk-your-pusula-key` durch einen in Pusula erstellten API-Schlüssel.
- Das `url`-Feld sollte auf `/api/v1/vscode/{token}/chat/completions` zeigen.
- Das `modelsUrl`-Feld sollte auf `/api/v1/vscode/{token}/models` zeigen.
- Bevorzugen Sie den normalen `/v1` + Bearer-Header-Flow, wenn der Client benutzerdefinierte Header unterstützt.
- URL-eingebettete Tokens sind ein Kompatibilitätsfallback und können in Editorprotokollen oder Proxyverläufen erscheinen.

## 10. Interne Pusula-CLI

Die Binärdatei `pusula` stellt Befehle für den Serverlebenszyklus, die Einrichtung, Diagnose und Providerverwaltung bereit. Einstiegspunkt: `bin/pusula.mjs`.

```bash
pusula                              # Server starten (Standardport 20128)
pusula setup                        # Interaktiver Einrichtungsassistent
pusula doctor                       # Konfiguration, DB, Ports und Laufzeit prüfen
pusula providers list               # Konfigurierte Providerverbindungen
pusula providers test-all           # Jede aktive Verbindung testen
pusula reset-password               # Administratorpasswort zurücksetzen
pusula logs                         # Anfrageprotokolle streamen
pusula health                       # Detaillierter Zustand (Unterbrecher, Cache, Arbeitsspeicher)
pusula --version                    # Version ausgeben
pusula --help                       # Alle Befehle anzeigen
```

### Einrichtung & Initialisierung

```bash
pusula setup                        # Interaktiver Einrichtungsassistent
pusula setup --non-interactive      # CI-/Automatisierungsmodus (liest Umgebungsvariablen + Flags)
pusula setup --password '<value>'   # Administratorpasswort direkt festlegen
pusula setup --add-provider \
  --provider openai \
  --api-key '<value>' \
  --test-provider                      # Provider in einem Schritt hinzufügen und testen
```

Erkannte Umgebungsvariablen für die nicht interaktive Einrichtung:

| Variable            | Zweck                                                                    |
| ------------------- | ------------------------------------------------------------------------ |
| `PUSULA_API_KEY` | Provider-API-Schlüssel (über Commander `.env()` an `--api-key` gebunden) |
| `DATA_DIR`          | Pusula-Datenverzeichnis überschreiben                                 |

Alle anderen nicht interaktiven Eingaben werden als Flags und nicht als Umgebungsvariablen übergeben:
`--password`, `--provider`, `--provider-name`, `--provider-base-url`, `--default-model`
(siehe die Optionen von `pusula setup` oben).

### Diagnose

```bash
pusula doctor                       # Konfiguration, DB, Ports, Laufzeit, Arbeitsspeicher und Erreichbarkeit prüfen
pusula doctor --json                # Maschinenlesbares JSON
pusula doctor --no-liveness         # HTTP-Zustandsprüfung überspringen
pusula doctor --host 0.0.0.0        # Host für die Erreichbarkeitsprüfung überschreiben
pusula doctor --liveness-url <url>  # Vollständige URL des Zustandsendpunkts überschreiben
```

Der Doctor führt folgende Prüfungen aus: `Config`, `Database`, `Storage/encryption`,
`Port availability`, `Node runtime`, `Native binary` (better-sqlite3),
`Memory` und `Server liveness`. Er wird mit einem von null verschiedenen Statuscode beendet, wenn eine Prüfung den Status `fail` hat.

### Providerverwaltung

```bash
pusula providers available                       # Pusula-Providerkatalog
pusula providers available --search openai       # Katalog nach ID/Name/Alias/Kategorie filtern
pusula providers available --category api-key    # Nach Kategorie filtern (api-key, oauth, free, ...)
pusula providers available --json                # Maschinenlesbares JSON

pusula providers list                            # Konfigurierte Providerverbindungen
pusula providers list --json

pusula providers test <id|name>                  # Eine konfigurierte Verbindung testen
pusula providers test-all                        # Jede aktive Verbindung testen
pusula providers validate                        # Rein lokale Strukturvalidierung
pusula providers add <provider> --credential-env PROVIDER_KEY
pusula providers import ./providers.json --dry-run --json
pusula providers auth <provider>                 # Bestehender OAuth-Ablauf
pusula providers edit <id|name> --default-model <model>
pusula providers remove <id|name> --yes
```

`providers add/import/auth/edit/remove` sind primär API-basiert und funktionieren daher mit
dem aktiven lokalen oder entfernten Kontext. Anmeldedaten sollten über
`--credential-stdin` oder `--credential-env` eingegeben werden; `--dry-run --json` meldet ausschließlich
redigierte Angaben zu Vorhandensein und Struktur. `providers available` liest den Pusula-Katalog;
`providers list/test/test-all/validate` behalten ihr lokales SQLite-Verhalten bei und
erfordern keinen laufenden Server.

### Wiederherstellung & Zurücksetzen

```bash
pusula reset-password                # Administratorpasswort zurücksetzen (auch: pusula-reset-password)
pusula reset-encrypted-columns       # Warnung + Probelauf zum Zurücksetzen verschlüsselter Anmeldedaten anzeigen
pusula reset-encrypted-columns --force  # Verschlüsselte Anmeldedaten in SQLite tatsächlich auf null setzen
```

### Export von Anmeldedaten (⚠ mit Vorsicht behandeln)

```bash
pusula auth export                                 # Warnung + Bestätigungsabfrage anzeigen — kein DB-Zugriff
pusula auth export --force                          # ENTSCHLÜSSELTE Anmeldedaten ALLER Verbindungen als JSON auf stdout exportieren
pusula auth export --force --id <id>                 # Nur die übereinstimmende Verbindung exportieren
pusula auth export --force --format env               # Zeilen im Format PUSULA_<PROVIDER>_<FIELD>=<value> ausgeben
pusula auth export --force --out creds.json           # In eine Datei schreiben (mit Berechtigungen 0600 erstellt)
```

`auth export` ist **rein lokal** (direktes Lesen aus SQLite, keine HTTP-Route) und gibt absichtlich
**Klartextwerte** für `apiKey`/`accessToken`/`refreshToken`/`idToken` aus bzw. schreibt diese — das ist die Funktion und kein
Fehler. Ohne `--force` wird nichts aus der Datenbank gelesen und nichts entschlüsselt. Vor jeder Klartextausgabe
wird stets ein Warnbanner auf stderr ausgegeben. Erfordert, dass `STORAGE_ENCRYPTION_KEY`
gesetzt ist. Ein Feld, dessen Entschlüsselung fehlschlägt (veralteter Schlüssel, beschädigter Geheimtext), wird als
`<field>DecryptFailed: true` gemeldet, anstatt den gesamten Export abzubrechen oder den zugrunde liegenden Fehler offenzulegen.

### Weitere Unterbefehle

Diese setzen einen laufenden Pusula-Server voraus, sofern nicht anders angegeben:

```bash
pusula status                       # Umfassender Laufzeitstatus
pusula logs                         # Anforderungsprotokolle streamen (--json, --search, --follow)
pusula config list                  # Konfigurierte CLI-Tools anzeigen

pusula provider list                # Verfügbare Anbieter auflisten (Alias für providers list)
pusula provider add                 # Pusula als Anbieter in einem Tool registrieren
pusula keys add | list | remove     # API-Schlüssel verwalten
pusula models [provider]            # Modelle auflisten (--json, --search)
pusula combo list | switch | create | delete

pusula backup                       # Momentaufnahme von Konfiguration und DB erstellen
pusula restore                      # Aus einer vorherigen Momentaufnahme wiederherstellen

pusula health                       # Detaillierter Systemzustand (Schutzschalter, Cache, Arbeitsspeicher)
pusula quota                        # Nutzung des Anbieterkontingents
pusula cache                        # Cache-Status
pusula cache clear                  # Semantik- und Signatur-Caches leeren

pusula mcp status | restart         # MCP-Serverstatus / Neustart
pusula a2a status | card            # A2A-Serverstatus / Agentenkarte

pusula tunnel list | create | stop  # Tunnel verwalten (cloudflare/tailscale/ngrok)
pusula env show | get <k> | set <k> <v>  # Umgebungsvariablen anzeigen / festlegen (temporär)

pusula test                         # Kurztest der Anbieterkonnektivität
pusula update                       # Nach Aktualisierungen suchen
pusula completion                   # Shell-Vervollständigung generieren
```

### Häufig verwendete Optionen

| Option              | Beschreibung                                                                  |
| ------------------- | ----------------------------------------------------------------------------- |
| `--no-open`         | Browser beim Start nicht automatisch öffnen                                   |
| `--port <n>`        | API-Port überschreiben (Standard: 20128)                                      |
| `--mcp`             | Als MCP-Server über stdio ausführen (für IDEs)                                |
| `--non-interactive` | CI-Modus (keine Eingabeaufforderungen; liest aus Umgebungsvariablen/Optionen) |
| `--json`            | Maschinenlesbare JSON-Ausgabe (doctor, providers usw.)                        |
| `--help`, `-h`      | Befehlsspezifische Hilfe anzeigen                                             |
| `--version`, `-v`   | Installierte Version ausgeben                                                 |

## Verfügbare API-Endpunkte

| Endpunkt                   | Beschreibung                   | Verwendung                                |
| -------------------------- | ------------------------------ | ----------------------------------------- |
| `/v1/chat/completions`     | Standard-Chat (alle Anbieter)  | Alle modernen Werkzeuge                   |
| `/v1/responses`            | Responses API (OpenAI-Format)  | Codex, agentische Workflows               |
| `/v1/completions`          | Legacy-Textvervollständigungen | Ältere Werkzeuge, die `prompt:` verwenden |
| `/v1/embeddings`           | Text-Embeddings                | RAG, Suche                                |
| `/v1/images/generations`   | Bildgenerierung                | GPT-Image, Flux usw.                      |
| `/v1/audio/speech`         | Text-zu-Sprache                | ElevenLabs, OpenAI TTS                    |
| `/v1/audio/transcriptions` | Sprache-zu-Text                | Deepgram, AssemblyAI                      |

Bereit zum Einfügen Beispiele mit einer tokenisierten Pusula-URL:

```txt
Token-Beispiel: sk-a3ab3c080beaee3a-69f4a4-070d71af

Standard OpenAI-Basis: http://localhost:20128/v1
VS Code-Modelle: http://localhost:20128/api/v1/vscode/sk-a3ab3c080beaee3a-69f4a4-070d71af/models
VS Code-Chat: http://localhost:20128/api/v1/vscode/sk-a3ab3c080beaee3a-69f4a4-070d71af/chat/completions
```

## Fehlersuche

| Fehler                                            | Ursache                          | Lösung                                                      |
| ------------------------------------------------- | -------------------------------- | ----------------------------------------------------------- |
| `Connection refused`                              | Pusula läuft nicht            | `pusula serve`                                           |
| `401 Unauthorized`                                | Falscher API-Schlüssel           | Überprüfen in `/dashboard/api-manager`                      |
| `No combo configured`                             | Keine aktive Routing-Kombination | Einrichten in `/dashboard/combos`                           |
| CLI zeigt "nicht installiert"                     | Binary nicht im PATH             | Überprüfen mit `which <command>`                            |
| Dashboard zeigt "nicht erkannt" nach Installation | Cache veraltet                   | Klicken Sie auf "⟳ Erkennung aktualisieren" im Dashboard    |
| Alter Link `/dashboard/cli-tools`                 | Lesezeichen vor v3.8.6           | Automatische Weiterleitung zu `/dashboard/cli-code` (308)   |
| Alter Link `/dashboard/agents`                    | Lesezeichen vor v3.8.6           | Automatische Weiterleitung zu `/dashboard/acp-agents` (308) |
