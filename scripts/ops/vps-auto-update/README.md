# pusula-auto-update

Pull-based auto-update for the Pusula Docker container on the VPS. The server
pulls `ghcr.io/ferhat-yasinoglu/pusula:main`; nothing ever connects to the server.

| File                         | What it is                                                                   |
| ---------------------------- | ---------------------------------------------------------------------------- |
| `pusula-auto-update`         | the updater, installed as `/usr/local/sbin/pusula-auto-update`               |
| `pusula-auto-update.service` | `Type=oneshot` unit that runs it                                             |
| `pusula-auto-update.timer`   | every 15 min (+ up to 3 min random delay) and 3 min after boot               |
| `install.sh`                 | one-paste installer, generated by `build-installer.sh` (do not edit by hand) |

## Install

On the server, as root, download `install.sh` from a pinned commit, check its sha256
and run it (replace `<commit>` and `<sha256>` with the values for the commit you
install; `sha256sum scripts/ops/vps-auto-update/install.sh` prints the hash):

```sh
curl -fsSLo /root/pusula-au-install.sh https://raw.githubusercontent.com/Ferhat-Yasinoglu/pusula/<commit>/scripts/ops/vps-auto-update/install.sh && echo '<sha256>  /root/pusula-au-install.sh' | sha256sum -c - && bash /root/pusula-au-install.sh
```

Pasting the whole of `install.sh` into a root shell also works (press Return if nothing
starts).

It writes the three files (sha256-checked, so a damaged paste installs nothing), enables
the timer, prints the commands below, and starts the first update **under systemd** while
showing its log. On a server that has been up for a while, enabling the timer already
starts that run (systemd elapses `OnBootSec=` at once when it is in the past); the
installer then shows that same run from its first line instead of starting a second one.
An SSH drop, the phone locking, or Ctrl-C only stops the watching; the update itself goes
on. At the end it prints the result and the commands again. The first run switches from
the locally built `pusula:base` to the ghcr image and may run many DB migrations; the
health gate allows 15 minutes.

## Everyday commands

| Task                 | Command                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------ |
| What is going on     | `pusula-auto-update --status`                                                                    |
| Logs                 | `journalctl -t pusula-auto-update -n 100 --no-pager` (follow: add `-f`)                          |
| Update now           | `pusula-auto-update` (runs under systemd; Ctrl-C only stops watching; exits with the run's code) |
| What would a run do  | `pusula-auto-update --dry-run` (changes nothing)                                                 |
| Go back one version  | `pusula-auto-update --rollback`                                                                  |
| Resume after a pause | `pusula-auto-update --reset`                                                                     |
| Disable / enable     | `systemctl disable --now pusula-auto-update.timer` / `systemctl enable --now ...`                |

## What one run does

1. **Recovers first.** Before every step that changes something, the run writes
   `/var/lib/pusula-auto-update/progress` (phase, old and new image, backup file,
   compose project). If a run was interrupted (power loss, reboot, SIGKILL, `systemctl
stop`), the next run (3 to 6 minutes after boot, or the signal handler itself)
   finishes it: a new container that is still running gets the full health gate and the
   update completes (unless its build is already recorded as bad); otherwise the old
   container is started again (or left alone if it was never stopped), or the backup is
   restored and the old image recreated. Each attempt counts once towards the pause and
   records its build as bad once, however many runs it takes to finish. The record is
   flushed to disk before it replaces the previous one; if it is still found empty or
   cut short, it is set aside when `pusula` runs healthy, otherwise the run stops with
   exit 2 and asks for a repair by hand. Recovery never refuses: when compose cannot
   recreate the container (the other compose, standalone or plugin, is tried too), it
   ends with exit 2 and the next run tries again.
2. **Never starts Docker.** If `docker.service` is stopped (even with `docker.socket`
   listening) it logs that and exits 0.
3. **Paused?** After 2 failed attempts in a row (any cause, including a failed backup
   while the container was stopped) it stops updating and says why until you run
   `pusula-auto-update --reset`.
4. **Refuses before pulling**, never after: container `pusula` and its compose labels,
   service `pusula-base`, image `pusula:base`, compose loads the project and sees the
   container (`ps -a`), `PUSULA_BASE_PATH` empty, current container healthy, free disk
   space for the pull, the backup and its extracted copy. Then it prunes dangling pusula
   images (superseded ghcr builds, old previous images) and pulls.
   Compose: the standalone `docker-compose` is used (1.29.2 negotiates the API version,
   so it also works with Docker Engine 29); if it cannot list the containers and the
   `docker compose` plugin is installed, the plugin is used instead. A relative
   `config_files` label written by docker-compose 1.x (relative to the directory it was
   started in, e.g. `cd /root && docker-compose -f pusula/docker-compose.yml`) is
   resolved from the working-dir label.
5. Same image as running: up to date. Image recorded as bad: skipped; a newer build is
   tried normally.
6. Stops only `pusula` (redis keeps running), backs up the data dir (the real directory,
   also if `data` is a symlink) to `/root/pusula-backups/data-<UTC>.tar.gz`, syncs, tags
   the new image `pusula:base` and recreates only that service with docker-compose
   (same project, files, profile; `--no-deps --no-build --force-recreate`).
7. **Health gate:** Docker health `healthy` within 15 min (`starting` or `unhealthy`
   while the container keeps running without restarts is not a failure: `/healthz`
   answers 503 until migrations are done), then healthy for 60 s more, then
   `/api/health/ping` must answer `{"status":"ok"}` if the old version did. An exit, a
   crash or a restart fails at once. Timing uses the time since boot, so a wall-clock
   step does not shorten or stretch it. Right after the new container is created, the
   backup is extracted next to the backups (the restore copy), while the disk still has
   the room checked before the pull.
   **Docker itself misbehaving** (dockerd restarted by a package upgrade, not
   answering) is not blamed on the build: while Docker does not answer the gate waits
   (up to 2 min, not counted against the 15) and the 60 s window starts over; when
   dockerd restarted (its start time changed, or the container was restarted without a
   crash) the whole gate starts over. A failure right after such an event is never
   recorded as bad. If Docker does not answer at all, the new container is left alone
   (exit 2, "undecided") and the next run checks it again.
8. **Success:** the old image becomes `pusula:previous`, recorded together with the
   backup taken just before it was replaced; backups rotate to the newest 5 (only files
   this tool recorded; hand-made files in the folder are never touched).
   **Failure:** the restore copy is checked (extracted again if needed) **before** the
   new container is removed, so a full disk leaves the container and the data as they
   are: the run then ends with exit 2 and `DISK FULL ... Free disk space` in the log and
   the result, and every later run retries until there is room. Then the new container
   is removed (waiting up to 2 min for a Docker that does not answer), the backup is put
   in place by rename (the new version's data is moved to `failed-data-<UTC>`, the newest
   2 are kept), the old image is recreated and must pass the health gate, and the build is
   recorded as bad.

`pusula:previous` moves only on a successful update. During an attempt the old image is
held by the temporary tag `pusula:rollback`.

## Rolling back by hand

`pusula-auto-update --rollback` restores the recorded `pusula:previous` image together
with the backup taken when it was replaced. The data written since then is moved to
`/root/pusula-backups/failed-data-<UTC>` (not deleted). The rolled-back build is recorded
as bad, so the timer (which stays on) does not re-apply it; a newer build is tried as
usual. It refuses with a clear message when there is nothing older (fresh install, or
already rolled back once), when the disk has no room to extract the backup (nothing is
changed then), and while an update is running (it does not wait: once that update has
finished, the target shown before may no longer be the right one; check `--status` and
run it again). It works also when the `pusula` container is stopped. `--status` shows
the rollback target.

## Settings

Optional `/etc/default/pusula-auto-update` (read by every mode):

```sh
PUSULA_AU_HEALTH_TIMEOUT=1800   # seconds to wait for "healthy" (default 900)
PUSULA_AU_STABLE_SECS=120       # seconds it must then stay healthy (default 60)
```

## Files on the server

- `/var/lib/pusula-auto-update/` (0700): `lock`, `progress` (only during an attempt;
  `progress.unreadable-<UTC>` if one was found empty and set aside),
  `previous` (rollback target), `backups` (backup metadata), `bad-images`, `failures`,
  `paused`, `last-result`, `failed-*.log` (last lines of a failed container, newest 3).
- `/root/pusula-backups/` (0700): `data-<UTC>.tar.gz`, `failed-data-<UTC>/`,
  `.restore-in-progress/` (the extracted restore copy, only during an attempt).

It never prints `.env` contents and never edits `docker-compose.yml`, `.env` or the git
checkout in `/root/pusula`.

## Exit codes

The same for a timer run, a run typed in a shell (it returns the run's code) and the
installer's first run:
`0` done, up to date, skipped, paused or Docker stopped; `1` refused, or failed and the
old version runs again; `2` the old version could not be brought back yet, Docker
stopped answering mid-update, or a rollback waits for disk space (the site may be down;
the next run tries again; to repair by hand, first
`systemctl disable --now pusula-auto-update.timer`, then delete
`/var/lib/pusula-auto-update/progress` when done).

## Development

```sh
./build-installer.sh       # regenerate install.sh from the three files
```

The updater was checked with shellcheck, `systemd-analyze verify` and a simulation
harness (fake docker, docker-compose 1.29/v2, systemctl, journalctl): 47 updater
scenarios, including crashes at every step, and 7 installer scenarios. The harness is not
part of the repository; nothing has run against a real Docker daemon before the first
install on the server.

Known limits: the backup is a single-threaded `tar -czf` of the whole data dir while the
container is stopped, so downtime grows with the data dir (Pusula's own `db_backups/`
included). Measure it on the server (`journalctl -t pusula-auto-update` shows the backup
start and end times) before deciding to exclude anything.
